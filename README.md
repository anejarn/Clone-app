# Sigma

Sigma is the application of Sigma SARL (Marrakech): short-term rental management and guest concierge, with condominium management (syndic) to follow in V2. See [`CLAUDE.md`](CLAUDE.md) for the product brief and [`TACHES_SIGMA.md`](TACHES_SIGMA.md) for the work plan by lot.

This repository is, for now, the guest-facing website: a French-first rental site covering ten Marrakech neighbourhoods (Hivernage, Guéliz, Médina, Palmeraie, Agdal, Targa, Route de l'Ourika, Agafay, Semlalia, Ménara), with homes, activities and concierge tabs, search with availability, favourites, accounts, stays (`/trips`) and a help page (`/aide`, including Sigma's offer to owners). Prices are in dirhams (MAD), dates in JJ/MM/AAAA, times in Africa/Casablanca; there is no guest service fee. Stays can be booked through the API only: there is no booking button and no payment in the UI yet. It started as a functional replica built from a recon of a large rental marketplace, used as functional inspiration only: name, logo (Σ), Majorelle-blue colours, texts and imagery are Sigma's.

History: the replica was built on 12–13 October 2026 under the working name Nidou; a ski-resort pivot was tried on 13–14 October and reverted on 14 October.
The app was renamed Sigma on 14 October 2026, with the pivot's generic fixes (search combobox, date label, input limits, help page, truthful cookie notice) ported back.

## Develop

Needs Node 22.18+, pnpm and Postgres 16.

```bash
cp .env.example .env          # then set BETTER_AUTH_SECRET (openssl rand -base64 32)
docker compose up -d          # Postgres 16: role `sigma` (password `sigma`), databases `sigma` and `sigma_test`
pnpm install                  # also generates the Prisma client
pnpm db:deploy && pnpm db:seed
pnpm dev                      # http://localhost:3000
```

| Command | What it does |
|---|---|
| `pnpm lint` / `pnpm typecheck` | ESLint, and route-type generation + `tsc` |
| `pnpm test` | Unit tests (`tests/unit`), no database; date tests also run under UTC+14 and UTC−8 |
| `pnpm test:integration` | Server logic against `sigma_test` (`tests/integration`): migrates and reseeds it first |
| `DATABASE_URL=<test db> pnpm build && pnpm test:e2e` | Playwright against the production build and `sigma_test`: user journeys, API contract, security, accessibility (axe), keyboard, timezones, design conformance; desktop and mobile |
| `pnpm test:coverage` | Unit + integration coverage of `lib/` |
| `pnpm db:migrate` | Create/apply a migration after editing `prisma/schema.prisma` |
| `pnpm db:seed` | Reload demo data (clears listings, bookings, reviews and favourites; keeps real accounts) |
| `pnpm guide:link <bookingId> [fr\|es\|en]` | Issue a new welcome guide link for a booking and print it (the previous link stops working) |
| `pnpm secrets:rotate` | Re-encrypt the guide's secrets with the current `ACCESS_CODES_KEY` and the travellers' fiches and document scans with the current `IDENTITY_DOCS_KEY` (after a key rotation) |
| `pnpm identity:purge [--dry-run] [--org=<slug>]` | Delete the travellers' identity data of the stays whose departure is older than the organization's retention delay (`--dry-run` only lists them). To run daily until lot 7's scheduler does |
| `pnpm db:reset` | Drop and recreate the database, then seed. Destructive, dev only |

To reseed the test database too: `DATABASE_URL="postgresql://sigma:sigma@localhost:5432/sigma_test?schema=public" pnpm db:seed`.

### Listing photos (uploads)

Photos uploaded in Biens are stored by `lib/storage/` (interface `FileStorage`). The only store for now writes to the local disk under `UPLOAD_DIR` (default `./uploads`, git-ignored: back it up with the database); choosing a cloud store (S3-compatible bucket, region, loi 09-08 transfer) is left to the associés, and plugs in by writing another `FileStorage` in `lib/storage/index.ts`. Files are served by `GET /media/<key>`: photos of published listings to anyone, a draft's photos only to staff of its organization. JPEG, PNG or WebP (checked by content), 5 MB at most, 30 per listing.

### Back-office access

`/admin` is for organization members with role ADMIN (associé, everything) or AGENT (agent terrain: Tableau de bord, Réservations, Calendrier, Mes tâches, Ma journée, Pannes). The sections and their roles are listed once in `lib/admin/sections.ts`; each page calls `requireAdminPage(href)`, each server action `requireAdminAction(href)` and each Route Handler `requireAdminApi(request, href)` (`lib/server/authz.ts`). Without a session, `proxy.ts` sends `/admin/*` to `/login?next=…` (HTTP 307); guests, owners and agents on an admin-only section get the "Page introuvable" page (the pages stream, so the status stays 200; the API answers 401/403); staff without double authentification are sent to `/admin/securite` to enroll (QR code or key, then backup codes). Roles and 2FA status are read from the database on every request, so a change applies at once.

### Bookings in the back-office

`/admin/calendrier` and `/admin/reservations` (ADMIN and AGENT) read every booking of the organization; amounts (nightly, cleaning, total) are sent to ADMIN only (`canSeeBookingAmounts`, `lib/admin/sections.ts`): an agent's data has no amounts at all. Writing (`/admin/reservations/nouvelle`, change of dates, cancellation) is ADMIN only, owner blocks included (`BOOKING_ENTRY_PATH`). Rules (`lib/server/admin/bookings.ts`): the home is a HOME of the organization (drafts allowed); departure after today, arrival at most two years ahead, 365 nights at most; overlaps with any confirmed booking or owner block are refused with the booking in the way (pre-check, then the `bookings_no_overlap` constraint under concurrent writes); a direct booking needs a name and a phone or e-mail and a channel, is priced by the pricing engine (each night at the home's base price or its season's or event's, + cleaning) unless a nightly price is typed (then every night at it; total > 0), and respects the stay's minimum (the home's, raised by the rules) unless the associé ticks « Accepter un séjour plus court » (noted in the audit trail); a platform booking needs its platform and code (unique per platform in the organization), its amount (total, of which cleaning) is optional and the stored nightly price is the average; changing a direct booking's dates re-prices it at its own nightly price, a platform booking keeps its total. Cancelling keeps the row (status CANCELLED); a stay that is over can't be changed or cancelled. Every write goes to `audit_logs` without the guest's contact. Colours are Sigma's own palette (text labels for the platforms, no logos), checked for contrast in `tests/unit/booking-sources.test.ts`.

### Prices (Prix)

`/admin/prix` (ADMIN only) holds the organization's price rules (`price_rules`, `price_rule_listings`): a **season** or an **event**, named, from a first to a last night (both included), one-off or every year (a range across 31/12 is fine), for every home, a selection or one home. A rule sets a percentage of the base price (−90 % to +500 %, rounded to the whole dirham, never under 1 MAD; 0 % = minimum stay only) or a fixed nightly price (one home only), and optionally a minimum stay. The engine (`lib/pricing/engine.ts`, pure, unit-tested in `tests/unit/pricing-engine.test.ts`) prices each night with one rule: one home > a selection > every home, then event > season, then priority (0–100), then the most recent; no rule = the listing's base price, untouched. A stay's minimum is the largest of the listing's `minNights` and the `minNights` of every rule covering one of its nights. Used by the quote and booking (`lib/server/bookings.ts`), search and homepage cards (stay totals, and only homes whose minimum fits the dates), and the team's direct bookings (preview in the browser with the same engine). Bookings store `nightlyCents` = the average of the nights (rounded to the centime) and `totalCents` = the exact sum. The base price and `minNights` of a home stay in Biens; its price calendar is at `/admin/prix/apercu?bien=<id>`. Prices don't go through iCal: report a change on each platform by hand (lot 7). The seed adds Marrakech demo rules for selections of homes (spring and autumn high seasons, year-end holidays with 3 nights minimum, Marathon 2027, Ramadan 2027).

### Field tasks (Opérations, Mes tâches)

Every confirmed guest stay (direct from the site or typed by the team, or a platform booking; any future import goes through the same function) gets three tasks, in the same transaction as the booking (`lib/operations/sync.ts`, `syncBookingTasks`): **linen** (arrival day, from check-out to check-in time), **welcome** (arrival day, check-in time + 2 h) and **cleaning** (departure day, from check-out to check-in time). Times are the organization's (`organizations.checkInMinutes` / `checkOutMinutes`, 15:00 and 11:00 by default) unless the home has its own (`listings.checkInMinutes` / `checkOutMinutes`; no settings screen yet), computed in Africa/Casablanca with the runtime's time zone rules, Ramadan's UTC+0 included (`lib/operations/schedule.ts`). Rules: owner blocks get no task (a cleaning after an owner's stay is added by hand); new dates move the tasks not started yet, and a time an associé typed survives a re-sync as long as the stay's dates don't change; a cancelled stay cancels its TODO tasks and keeps the started and done ones; a cleaning is flagged « Départ et arrivée le même jour » when another stay or an owner block arrives that day; no task is created for a day already past; generation is idempotent (one task per booking and type, `tasks_bookingId_type_key`).

Each task gets a copy of its type's check-list (`checklist_templates`, French defaults in `lib/operations/checklist.ts`: rooms, bathroom, kitchen, bins, linen, photos of each room…; keys, Wi-Fi, house rules, meter photo…). `/admin/operations` (ADMIN) lists the tasks by day (filters: dates, home, agent or « non affectées », status, type), assigns them (active ADMIN or AGENT of the organization only, also checked by the `tasks_assignee_check` trigger), changes their day and times, notes, cancels and reopens them, and adds manual tasks; `/admin/mes-taches` (ADMIN, AGENT) shows the tasks assigned to the person signed in for today and tomorrow, on a phone first: start, tick, take photos (`capture="environment"`, JPEG/PNG/WebP, shrunk in the browser above 600 KB, 5 MB at most, stored by `lib/storage` under `tasks/<organization>/<task>/`), finish. **An agent only sees and acts on the tasks assigned to them** (an unassigned or a colleague's task is « introuvable »); an associé on every task. A task becomes « fait » only when every item is ticked and every item that requires a photo has one, checked by the server in a transaction holding the task's row. Task photos are served by `/media` only to the organization's staff, never cached. Assignments, new times and status changes are audited; deactivating a member or giving them a non-staff role puts their open tasks back to « non affectée ». The dashboard counts today's tasks and the unassigned ones, and the open and urgent breakdowns.

After the migration `20261025090000_field_tasks` on a database with real bookings, run `pnpm tasks:backfill` once (idempotent) to create the tasks of the stays already there: the migration doesn't, because the Postgres time zone data can lag behind for Morocco (Ubuntu 24.04's stops at September 2026). `pnpm db:seed` does it for the demo data and shares the coming week's tasks between the two demo agents.

### Breakdowns (Pannes)

`/admin/pannes` (ADMIN, AGENT) lists the breakdown reports (`tickets`), most urgent first, open ones by default (signalée, en cours, en attente); associés filter by status, priority, category, home and assignee. Anyone of the team reports one from « Signaler une panne » (`/admin/pannes/nouvelle`), from a task's page or from Ma journée (`?tache=<id>`: the task's home and stay are linked; an agent only from their own tasks): home, what is wrong, category (plomberie, électricité, climatisation, électroménager, serrure, autre), priority (basse, normale, haute, urgente), details and a photo (taken with the phone's camera, shrunk in the browser like the task photos, stored by `lib/storage` under `tickets/<organization>/<ticket>/`). A ticket's page shows its photos (more can be added), its thread (`ticket_events`: reported, comments, every change with who and when) and what the person may do (`lib/operations/tickets.ts`): an **associé** sees every ticket and assigns it (active ADMIN or AGENT of the organization), changes its priority and status (cancel and reopen included) and types its cost in MAD with « À refacturer au propriétaire » (stored as `costCents` + `rechargeOwner`; the owner statements of lot 6 will read them); an **agent** sees only the tickets they reported or are assigned to — anything else is « Panne introuvable » — comments and adds photos, and the agent assigned moves it to en cours, en attente (d'une pièce or d'un prestataire) or réparée, never cancels or reopens it. Agents never see a cost, not even in the thread. Ticket photos are served by `/media` only to the associés and to the agents who can see the ticket, never cached. Creation, status, assignment, priority and cost changes go to `audit_logs`. Urgent open tickets are listed at the top of the dashboard, with counters of open and urgent ones. Database rules (migration `20261026090000_tickets_and_field_sync`): status dates match the status, « en attente » says of what, a cost needs a value to be re-invoiced, the stay and the task are of the ticket's home, the assignee is ADMIN or AGENT of the organization (`tickets_check` trigger).

### Ma journée (offline)

`/admin/ma-journee` (ADMIN, AGENT) shows the tasks assigned to the person signed in for today and tomorrow (Marrakech), on a phone first, with or without network. It can be installed on the home screen (« Ajouter à l'écran d'accueil »): the back-office links the team app's manifest `/equipe.webmanifest` (Sigma Équipe, French, Majorelle blue, the Σ icons in `public/icons/`, start page Ma journée); the public site links none.

- **Data on the device**: the page gets the day from `GET /api/admin/journee` (the person's own tasks with their check-lists; no amounts, no access codes — none exist yet) and keeps it in IndexedDB (`sigma-journee`, `lib/offline/`). Every change — start, tick, photo, remark, finish — is queued there first (photos as Blobs, shrunk before), shown at once, and sent in order to `POST /api/admin/journee/operations` as soon as the device is online (at once, on the `online` event, or with « Synchroniser »). The page shows « En ligne » / « Hors connexion » and how many changes wait. Finishing offline is checked on the device with the same rule as the server (every item ticked, a photo for every item that needs one, queued photos included).
- **Idempotency and conflicts**: each change carries an id made on the phone (`crypto.randomUUID()`); the server decides it once per person and id and records the outcome (`task_sync_operations`), so a retry after a lost answer changes nothing and gets the same answer, even when two copies race. The server wins: a task taken from the agent (reassigned, unassigned) or cancelled meanwhile refuses the change, already-met intents are fine (starting a task in progress, finishing a task done), an incomplete finish is refused with what is missing; refused changes are listed on the page with the reason (`lib/operations/field-ops.ts`). Only the caller's own tasks are reachable, associés included. Status changes are audited with `offline: true`; the agent's remarks (`tasks.fieldNotes`) show in Opérations and Mes tâches as « Remarques de l'agent ».
- **Service worker** (`public/sw-journee.js`, served with `Cache-Control: no-cache, no-store`): registered by Ma journée only, with the scope `/admin/ma-journee`, in production builds only. It keeps that page (network first; the copy is dropped when the server sends the visitor away) and the app's static files (`/_next/static/…`, icons) so that the page opens without network; it never keeps another page, an API answer or a photo. Every sign-out button (`lib/sign-out.ts`) first asks before losing unsent changes, then deletes the IndexedDB database and the `sigma-journee-*` caches and unregisters the worker; the back-office's sign-out then reloads the login page.
- **Limits**: the day is today and tomorrow only; task photos already sent are not kept offline (their count is); a photo of a task in progress taken on two phones goes in twice; the records of `task_sync_operations` should be purged after 30 days by the background jobs (lot 7); iOS keeps a home-screen app's data only while it is used regularly.

### Welcome guide (Guide d'accueil)

Each stay can have a **secret link** `/guide/<token>`: 32 random bytes (256 bits), looked up by its SHA-256 (`guide_links.tokenHash`) and also kept encrypted so the associés can copy it again. On the booking's page (Réservations, **ADMIN only**), « Guide d'accueil » creates the link, shows it with « Copier le lien » and « Partager sur WhatsApp » (message in the guest's language), « Régénérer » (the old link stops working) and « Révoquer », and sets the guest's language. Owner blocks and cancelled stays have no guide (404); a link stops working 30 days after the stay. The guest needs no account.

- **Content** (Biens → a home → tab « Guide d'accueil », ADMIN): maps link (default: the home's coordinates), directions and access instructions (French, plus Spanish and English variants; French is shown when one is missing), access photos (shown only through the guide link), Wi-Fi name and password, access codes (porte, boîte à clés, alarme, portail, parking…), house rules (French from the fiche, es/en here), the home's recommendations (category, text in three languages, link) and, unless turned off, the organization's common ones. « Guide d'accueil : réglages communs » (from Biens) holds the conciergerie's phone and WhatsApp (organization parameters) and the common recommendations. Check-in/check-out times are the organization's or the home's (no settings screen yet). The guide page lists every change and every reveal of the codes.
- **Secrets**: codes, Wi-Fi passwords and link tokens are encrypted with AES-256-GCM (`lib/secrets/access-codes.ts`, `node:crypto`) under `ACCESS_CODES_KEY` (32 bytes in base64; each value carries its key id; older keys go in `ACCESS_CODES_PREVIOUS_KEYS`, then `pnpm secrets:rotate`), each value bound to its organization, home or booking and purpose. In production nothing is encrypted or shown without the key; development and tests use a public development key. The database refuses anything that isn't an envelope. The team sees them only on request: associés on the guide page (« Afficher les codes »), **agents only from a task assigned to them today or tomorrow** (Mes tâches → the task → « Afficher les codes »), never in Ma journée (nothing secret is kept on a phone); every reveal is written to `audit_logs` (without the values).
- **Guest page**: mobile first, Sigma blue, sections Accès (address, « Ouvrir l'itinéraire », instructions, photos, codes), Wi-Fi, Règles, Bonnes adresses, Services (« Bientôt » until Lot 4b), Contact (conciergerie; Police 19, Pompiers et ambulance 15, Gendarmerie royale 177) and a sticky bar « Appeler » / « WhatsApp ». **Codes and the Wi-Fi password are only in the page from the check-in time on the arrival day to the check-out time on the departure day**, Marrakech time computed with the runtime's time zone rules (Ramadan's UTC+0 included; never Postgres'); before, « Les codes seront affichés ici à partir du JJ/MM/AAAA à 15:00 » with a countdown that reloads the page at that time; after, hidden. Never an amount, a note, the guest's contact or the owner (`lib/server/guide/guest.ts` builds the payload field by field). `proxy.ts` checks the link first so that a dead link is a real 404; `Cache-Control: private, no-store`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`; outside the team service worker's scope; 30 failed lookups per client address in 10 minutes block that address until the window ends (address from `X-Forwarded-For` / `X-Real-IP`, which the hosting's proxy must set; no limit without them).
- **Languages** (`lib/i18n/`): typed catalogs `messages/fr.ts` (reference), `es.ts`, `en.ts` (a missing key is a type error); language from `?lang=`, else the booking's guest language, else `Accept-Language`, else French; switcher FR · ES · EN; the guide sets `lang`/`dir` (Arabic will be `rtl`). Adding a language: a catalog plus an entry in `lib/i18n/locales.ts`. No translation provider: `lib/i18n/translate.ts` is the hook for one (choice and loi 09-08 transfer left to the associés). Only the guide is translated; the public site stays French.
- **Demo**: the seed (dev and test databases, never production) fills a guide for every home (texts in fr/es/en, two codes, Wi-Fi), the conciergerie's contact, common recommendations, and two links with known tokens: `/guide/demo-guide-current-stay-0000000000000000000` (a stay in progress: codes shown) and `/guide/demo-guide-upcoming-stay-000000000000000000` (a stay to come, in English). For any other booking: `pnpm guide:link <bookingId>`, or the booking's page. After pulling this lot, the dev database needs `pnpm db:deploy` (and `pnpm db:seed` for the demo guides, which reloads the demo data).

### Travellers' declaration (Déclarations) and taxe de séjour

> **Legal values to confirm — nothing here is a legal fact.** The DGSN's télé-déclaration format, the retention delay of identity data (loi 09-08, CNDP) and the rates and exemptions of the taxe de séjour in Marrakech are **not known to the app**: Sigma must confirm them (lawyer, préfecture/DGSN, commune, accountant). The defaults below are placeholders, shown as such in the app.

- **Fiches de police** (`travelers`): per stay, one fiche per traveller — nom, prénom, sexe, date et lieu de naissance, nationalité, type de pièce (CIN marocaine, passeport, titre de séjour, autre), numéro, date et pays de délivrance, date d'expiration, adresse, pays de résidence, profession, dates d'arrivée et de départ (default: the stay's), provenance, destination. No signature. Adults (18 and over on arrival) need the names, sex, birth date, nationality and document; **minors** may be recorded too, linked to an adult of the stay (`guardianId`, checked by the `travelers_guardian_check` trigger), without a document. The booking's counts (adults, children) stay as they are; the fiches complete them.
- **Encryption** (`lib/secrets/identity.ts`, generic part `lib/secrets/envelope.ts` shared with the guide): every personal field of a fiche is one AES-256-GCM envelope (`travelers.identityEnc`, checked by `travelers_identity_check`: the database refuses clear text), bound to its organization, stay and traveller; document photos/scans (JPEG, PNG, WebP or PDF by content, 5 MB, 4 per traveller) are encrypted **before** they reach `lib/storage` (`identity/<org>/<booking>/<random>.enc`, binary envelope `SGE1…`), never served by `/media`, only by `GET /api/admin/declarations/documents/<id>` to the associés (decrypted, `no-store`, audited). Key: `IDENTITY_DOCS_KEY` (32 bytes in base64), separate from `ACCESS_CODES_KEY`; older keys in `IDENTITY_DOCS_PREVIOUS_KEYS`, then `pnpm secrets:rotate`. **Fails closed in production** without the key; development and tests use a public development key. In clear only: minor or not, the accompanying adult's id, declared or not (when, by whom).
- **Who**: the associés (ADMIN) list, search (name or document number, decrypted in memory), view, add, correct, delete and declare every fiche from **Déclarations** (`/admin/declarations`, `/admin/declarations/<bookingId>`) and the booking's page (« Voyageurs et taxe de séjour », counts only). An **agent** only from the welcome task (CHECKIN) assigned to them, today or tomorrow, neither done nor cancelled: Mes tâches → the task → « Saisir les voyageurs » (`/admin/mes-taches/<id>/voyageurs`, phone first, the camera opens for the document photo, shrunk on the phone); they add and correct that stay's fiches, never see a document photo, and see nothing once the task is done (`lib/declarations/access.ts`). Anyone else, or another organization: « introuvable ». **Every reading of decrypted fiches, every export, every change and every view of a scan is audited** (`travelers.viewed`, `declaration.exported`, `traveler.*`), with ids and counts only.
- **Exports for the DGSN** (`lib/declarations/`, behind the `DeclarationExporter` interface so the official format can be plugged in): a **CSV** (UTF-8 with BOM, `;`, CRLF, dates JJ/MM/AAAA, formula injection neutralised) with the usual fields of the fiche de police plus the establishment (home, address, loi 80-14 number) and the stay's reference, and **printable fiches individuelles** (HTML, one per page, to print or save as PDF). Filters: arrivals from/to, home, not declared only. Generated on the fly, never stored, ADMIN only, audited. **« Format à valider avec la DGSN / la préfecture »** is shown on the page and in the files. « Marquer comme déclaré » records `declaredAt`/`declaredById` for the stay's travellers (and can be taken back).
- **Undeclared arrivals**: stays arriving yesterday or today (Marrakech) with no adult fiche or an adult not declared; on the dashboard (« Arrivées des dernières 24 h non déclarées », associés) and at the top of Déclarations.
- **Retention and automatic deletion**: `organizations.identityRetentionDays` (Paramètres; 1–3650; **default 365 = placeholder, « délai légal à confirmer par Sigma / avocat — loi 09-08, CNDP »**), counted from the stay's departure. `pnpm identity:purge` (`lib/server/declarations/purge.ts`) deletes the scans from the store first, then the fiches, for every stay whose departure + delay is today or past, and leaves a trace without personal data (`identity_purges`: booking id, counts, delay, date; audit `identity.purged`); `--dry-run` logs what it would delete and changes nothing. Until lot 7's background scheduler runs it daily, run it every day (cron). The booking's contact (guest name, phone, e-mail) is not part of this purge.
- **Taxe de séjour** (`lib/tax/engine.ts`, pure, unit-tested in `tests/unit/tourist-tax.test.ts`): tax = Σ over the nights of rate × taxable guests, in centimes, **no rounding** (rates have at most two decimals; the total is exact, never rounded to the dirham). Rates are **versioned by effective date** (`tourist_tax_rates`, Paramètres): a night uses the latest version in force on it, so a new rate never changes earlier nights and a stay across a change is taxed night by night; a home may have its own rate from a date (`listing_tourist_tax_rates`; « revenir au taux de l'organisation »). **Exemptions** are per version: minors under an age (default on, under 18) and optionally the residents of Morocco; nothing else is assumed. Guests are the recorded travellers (age on arrival, residence) completed by the booking's counts — the tax is never lower because a fiche is missing. A version can be deleted only before it applies; new versions start today or later (the first one may start in the past). Each stay has a **snapshot** (`booking_tourist_taxes`: total, night-by-night lines, basis), computed when travellers are recorded or changed, when the dates change, or with « Calculer », until an associé **closes** it (« Clôturer »; reopening audited). The booking's page shows it; **Déclarations → Taxe de séjour par mois** gives the month's nights and tax by home (from the snapshots; a stay without one is estimated from its booking and flagged), with a CSV export. **No rate is a legal value**: the seed adds a **demo placeholder rate of 10,00 MAD labelled « TAUX FICTIF DE DÉMONSTRATION »** (dev and test databases only); a production organization starts without any rate (no tax computed, flagged « aucun taux »). A platform that collects the tax itself is not handled yet.
- **Demo**: the seed (dev and test databases only) adds two obviously fictitious travellers (« DEMO-VOYAGEUR Alpha/Bravo », documents `TEST000001`/`TEST000002`, declared) on the stay in progress. After pulling this lot: `pnpm db:deploy`, set `IDENTITY_DOCS_KEY` in production.

### Users and invitations

`/admin/utilisateurs` (ADMIN only) lists the organization's members and invites new ones as OWNER, AGENT or ADMIN. An invitation is a link `/invitation/<token>`: 256 random bits shown once to the admin, stored only as a SHA-256 hash, valid 7 days and once; "Renvoyer" issues a new link (the old one stops working), "Révoquer" cancels it. The invitee creates a name and password, or, if an account with that e-mail exists, signs in and accepts (an account of another organization can't be moved); staff are then sent to double authentification enrollment. Public sign-up still always gives a GUEST without organization. No e-mail or WhatsApp provider is chosen yet: messages go through `lib/notifications/` (interface `Notifier`, default sends nothing; `NOTIFICATIONS_DRIVER=console` prints them in development), so the admin copies the link or uses the "Partager sur WhatsApp" wa.me link. A member's page changes the role (refused for the last active ADMIN and for an owner who still owns listings), resets double authentification (acting admin's password + confirmation, never on oneself) and deactivates or reactivates the account (no sign-in, nothing deleted). Role changes, 2FA resets and deactivations revoke the person's sessions; every such action is written to `audit_logs` (who, what, target, when). Rules: `lib/server/admin/users.ts`, `lib/server/invitations.ts`.

### Docker volume created before the rename

A Postgres volume created when the app was still called Nidou has a `nidou` role and `nidou` / `nidou_test` databases. Rename them in place, keeping every row; do not delete the volume. Stop the app first (no open connections to the databases), then:

```bash
docker compose exec -T db psql -U nidou -d postgres <<'SQL'
CREATE ROLE sigma_tmp LOGIN SUPERUSER PASSWORD 'tmp';
SQL
docker compose exec -T db psql -U sigma_tmp -d postgres <<'SQL'
ALTER ROLE nidou RENAME TO sigma;
ALTER ROLE sigma WITH PASSWORD 'sigma';
ALTER DATABASE nidou RENAME TO sigma;
ALTER DATABASE nidou_test RENAME TO sigma_test;
SQL
docker compose exec -T db psql -U sigma -d postgres -c "ALTER ROLE sigma_tmp NOLOGIN;"
```

A role cannot rename itself while connected, hence the temporary role, disabled at the end (it owns nothing). Then update `DATABASE_URL` in `.env` as in `.env.example`.

## Backend at a glance

- **Data**: Postgres via Prisma 7 (`prisma-client` generator + `@prisma/adapter-pg`). Schema in `prisma/schema.prisma`; integrity rules Prisma can't express (no overlapping stays, value checks) are hand-written in the first migration.
- **Server code**: `lib/server/` (`catalog`, `bookings`, `wishlist`, `reviews`, `auth`), plain async functions that tests call directly. Pages use the cached wrappers in `lib/data/repo.ts` (`"use cache"`, tags `listings` and `availability`).
- **Auth**: [Better Auth](https://www.better-auth.com) with email + password and the Prisma adapter, chosen over Auth.js v5 (still in beta; its maintainers moved to Better Auth).
- **API**: `app/api/*`, documented in [`docs/api.md`](docs/api.md).
- **QA**: findings, fixes, Lighthouse and parity results in [`docs/qa-report.md`](docs/qa-report.md).

Next.js 16 runs with Cache Components: data functions use `"use cache"` + `cacheLife`, and anything that reads request data (params, search params, cookies) must sit inside `<Suspense>`. See `AGENTS.md` and the docs bundled in `node_modules/next/dist/docs/`.
